# Что импортируется из 1С: таблицы Firebird и журнал MongoDB

Справочник для разбора «что откуда взялось»: какие таблицы HiTek наполняет обмен с 1С,
какие в них ключевые поля, и как по журналу MongoDB понять, **когда именно** появилась
запись.

Цифры — с копии боевой базы `erp_base_api` и журнала `c1_data` (проверено 2026-08-13).

---

## 1. Цепочка «объект 1С → процедура → таблицы»

| Город | `/C1_City` | `EXP_CITY_IU` | `STR_CITY` |

| Группа номенклатуры | `/C1_Catalog` | `EXP_CATALOG_IU` | `OBJ_CATALOG` (рекурсивно по родителю) |
| Номенклатура | `/C1_Nomenklature` | `EXP_NOM_IU` | `C1_NOM`, `C1_LINKS`, `OBJ_LIST`, `NOM_LIST` |

та — свою группу и единицу измерения, и так далее.

## 2. Таблицы Firebird: основные поля

### 2.1 Мост «1С ↔ HiTek» — главное для разбора

**`C1_LINKS`** (6 137) — соответствие кода 1С и номенклатуры HiTek. Ключевая таблица:
через неё выясняется, какой позиции 1С отвечает какая позиция HiTek.

| Поле | Смысл |
|---|---|
| `KOD_IZD`, `ART_IZD` | код и артикул номенклатуры **из 1С** (пара — ключ сопоставления) |
| `NOM_ID` | позиция в `NOM_LIST` (HiTek) |
| `OBJ_ID` | объект в `OBJ_LIST`; в исторических данных не заполнен |
| `USER_ID` | кто создал связь |
| **`DATE_MOD`** | **когда связь создана/изменена** — заполнена у всех 6 137 строк, диапазон 08.11.2023 … 19.03.2024 |

Нюанс: у одной позиции законно бывает **две строки** — пара «код + артикул карточки» и
«код + артикул строки заказа»; по последней резолвится `NOM_ID` в `C1_ZAKAZ_I_S`.

**`C1_NOM`** (4 797) — карточка номенклатуры как её прислала 1С: `KOD_IZD`, `ART_IZD`,
`NAME_IZD`, `BARCODE_IZD`. Меток времени нет.

| Таблица | Строк | Основные поля |
|---|---:|---|
| `DOC_HEADER` | 515 | `DOC_ID`, `OPERATION` (5 — приход излишков, 7 — заказ в производство), **`DATE_DOC`**, `NUMBER`, `STORAGE_IN`/`STORAGE_OUT`, `PACK_ID` (изделие запуска), `PACK_CNT`, `DESCRIPT`, `REGISTED`, `DELETED` |

`DOC_ITEMS` — намерение (что планировали), `NOM_TRANS` — факт (что реально прошло).
Для отчётности источник истины — `NOM_TRANS`.

## 3. Метки времени в Firebird: чем датировать импорт

Собственной колонки «когда импортировано» у большинства таблиц **нет**. Реально
пригодны три:

| Поле | Таблица | Что означает | Диапазон в базе |
|---|---|---|---|
| **`DATE_INPORT`** | `C1_ZAKAZ_H` | момент импорта заказа | 15.12.2023 01:15:32 … 10:59:29 |
| **`DATE_MOD`** | `C1_LINKS` | создание/изменение связи с 1С | 08.11.2023 … 19.03.2024 |
| **`DATE_CREATE`** | `BOM_LIST` | создание спецификации | 08.11.2023 … 15.12.2023 |

`DATE_DOC` (в `DOC_HEADER`) и `DATE_TRANS` (в `NOM_TRANS`) — **даты документа и движения,
а не импорта**: они могут быть задним числом. `DATE_TRANS` к тому же только дата, без времени.

У справочников (`GLB_MEASURE`, `STR_FIRM`, `STR_STORAGE`, `OBJ_CATALOG`), у `C1_NOM`,
`NOM_LIST`, `BOM_ITEMS` меток времени **нет вообще** — когда они появились, можно узнать
только по журналу MongoDB (раздел 4).

## 4. MongoDB — журнал обмена

База `c1_data`. **Основное назначение — лог: что и когда импортировано**, плюс
соответствие «GUID 1С ↔ ID в HiTek», по которому работает защита от повторного импорта.

### 4.1 Коллекции

| Коллекция | Документов | Что хранит | Путь к GUID внутри документа |
|---|---:|---|---|
| `C1_ZC` | 462 | заказы покупателей | `response.ЗаказПокупателя.GUIDЗаказаПокупателя` |
| `C1_Nom` | 4 721 | номенклатура | `response.Номенклатура.GUIDНоменклатуры` |
| `C1_Bom` | 1 378 | спецификации | `response.Спецификация.GUIDСпецификации` |
| `C1_Partner` | 854 | контрагенты | `response.Контрагент.GUIDКонтрагента` |
| `C1_Catalog` | 264 | группы номенклатуры | `response.ГруппаНоменклатуры.GUIDГруппыНоменклатуры` |
| `C1_Storage` | 97 | склады/подразделения | `response.СтруктурноеПодразделение.GUIDСтруктурнойЕдиницы` |
| `C1_Measure` | 8 | единицы измерения | `response.ЕдиницаИзмерения.GUIDEдиницыИзмерения` |
| `C1_City`, `C1_Country` | 0 | города и страны — не использовались | — |
| `log.connections` | 115 | лог подключений сервиса к MongoDB | — |

Остатки (`/C1_nomenclature_cnt`) в журнал **не пишутся** — у их схемы нет коллекции.

### 4.2 Структура документа

Ключи верхнего уровня: `_id`, `PRM`, `error`, `response`, `GUID`, `res`.

- `response` — **сырой ответ 1С как есть** (по нему видно, что именно прислала 1С);
- `GUID` — GUID, по которому запрашивали (дописан сервисом);
- `PRM`, `error` — служебные поля ответа 1С (`SchemeName`, `Version`);
- **`res`** — результат импорта, добавляется сервисом:

```json
"res": { "insert_at": "2023-12-14T20:15:32.777Z", "ref_id": 2 }
```

| Поле | Смысл |
|---|---|
| **`res.insert_at`** | **когда запись добавлена в журнал** — фактический момент импорта объекта |
| `res.ref_id` | идентификатор, присвоенный объекту в HiTek (`ID_ZAKAZ`, `NOM_ID`, …) |

`log.connections` — по документу на каждый запуск сервиса: `{ date, username }`.
115 записей = 115 подключений; полезно, чтобы понять, когда сервис вообще работал.

### 4.3 Полезные запросы к журналу

```javascript
// когда шёл импорт: первая и последняя запись по коллекции
db.C1_ZC.aggregate([{ $group: { _id: null,
  first: { $min: "$res.insert_at" }, last: { $max: "$res.insert_at" }, cnt: { $sum: 1 } } }])

// импорт по дням
db.C1_Nom.aggregate([
  { $group: { _id: { $dateToString: { format: "%Y-%m-%d", date: "$res.insert_at" } }, cnt: { $sum: 1 } } },
  { $sort: { _id: 1 } }])

// найти объект по GUID и узнать его ID в HiTek
db.C1_Nom.findOne({ "response.Номенклатура.GUIDНоменклатуры": "<GUID>" }, { "res": 1 })

// обратно: по ID в HiTek найти GUID 1С
db.C1_Nom.findOne({ "res.ref_id": 2630 }, { "response.Номенклатура.GUIDНоменклатуры": 1 })

// когда сервис запускался
db.getCollection("log.connections").find().sort({ date: 1 }).limit(5)
```

## 5. Как сопоставлять журнал и базу: две ловушки

**1. Часовые пояса.** MongoDB хранит время **в UTC** (ISO с `Z`), Firebird —
**в местном времени сервера БД, без указания зоны**. На исторических данных разница
ровно **5 часов** (Asia/Yekaterinburg). Проверено на одной и той же записи:

| ref_id | `res.insert_at` (Mongo, UTC) | `DATE_INPORT` (Firebird, местное) |
|---:|---|---|
| 2 | 2023-12-14 **20:15:32.777** | 2023-12-15 **01:15:32.682** |

Совпадение до десятых долей секунды — это одно и то же событие. Перед сравнением дат
приводите к одной зоне, иначе импорт «уедет» на сутки назад.

**2. Дубли в журнале.** Документов больше, чем объектов: `C1_ZC` — 462 при 441 заказе.
Один и тот же `ref_id` встречается в нескольких документах (например, у `ref_id = 2` их
два, с разным `insert_at`) — следы повторных прогонов. При подсчётах группируйте по
`res.ref_id`, а не считайте документы.

## 6. Как зайти в базу HiTek и посмотреть импортированное

### 6.1 Подключение к базе

Боевая установка (сеть заказчика): сервер **`192.168.10.65`**, база — алиас
**`erp_base_api`**, пользователь **`SYSDBA`**.

| Инструмент | Строка подключения |
|---|---|
| `isql` (Firebird) | `isql -user SYSDBA -password <пароль> 192.168.10.65:erp_base_api` |
| IBExpert / FlameRobin / DBeaver | сервер `192.168.10.65`, порт `3050`, база `erp_base_api`, пользователь `SYSDBA` |
| Строка для fb-port (`.env`) | `DB_HOST=192.168.10.65`, `DB_PORT=3050`, `DB_NAME=erp_base_api` |

**Пароль здесь намеренно не записан** — этот файл лежит в публичном GitHub-репозитории.
Взять его можно из `.env` рабочей установки C1CServ (переменная `DB_PASSWORD`) или из
`.env` fb-port. Тот же формат подключения годится и для наших тестовых баз, например
`firebird5.home.lan:erp_base_api_c1`.

Проверка, что подключились к нужной базе:

```sql
select rdb$get_context('SYSTEM','ENGINE_VERSION') as ENGINE,
       (select mon$database_name from mon$database) as DB_FILE
  from rdb$database;
```

### 6.2 Что открыть в самом HiTek

Приложение `HiTek.exe` читает те же таблицы напрямую (к Node-сервисам не обращается),
поэтому результат импорта виден в обычных формах:

| Что смотрим | Путь в программе | Таблицы |
|---|---|---|
| **Заказы из 1С** | меню `Документы` → `Список заказов из 1С` | `C1_ZAKAZ_H` |
| Строки заказа и привязка к номенклатуре | двойной клик по строке списка → карточка «Заказ» | `C1_ZAKAZ_I`, `C1_ZAKAZ_NOM_I`, `C1_ZTOD` → `DOC_HEADER` |
| **Соответствие кодов 1С и номенклатуры** | меню `Документы` → `Номенклатуры 1С` | `C1_NOM`, `C1_LINKS` |
| Остатки и цены из 1С | из «Номенклатуры 1С» кнопкой правки | `C1_AVAIL*` |
| Номенклатура, группы, спецификации | обычные справочники и спецификации | `NOM_LIST`, `OBJ_CATALOG`, `BOM_LIST` |

Ориентир, что данные на месте: в списке заказов должны быть номера вида `СИ00-0079xx`
с датой импорта **15.12.2023**.

### 6.3 То же самое запросами, без клиента

```sql
-- заказы: сколько и когда импортированы
select count(*) as ZAKAZOV, min(date_inport) as PERVYY, max(date_inport) as POSLEDNIY
  from c1_zakaz_h;

-- последние импортированные заказы
select first 10 id_zakaz, num, data_z, name_zak, date_inport
  from c1_zakaz_h order by date_inport desc;

-- строки конкретного заказа с привязкой к номенклатуре HiTek
select zi.id_zakaz_i, zi.kod_izd, zi.name_izd, zi.cnt, zn.nom_id, n.name
  from c1_zakaz_i zi
       left join c1_zakaz_nom_i zn on zn.id_zakaz_i = zi.id_zakaz_i
       left join nom_list n on n.nom_id = zn.nom_id
 where zi.id_zakaz = 441;

-- соответствие кода 1С и номенклатуры HiTek
select first 10 l.kod_izd, l.art_izd, l.nom_id, n.name, l.date_mod
  from c1_links l left join nom_list n on n.nom_id = l.nom_id
 order by l.date_mod desc;

-- что импорт создал в номенклатуре
select count(*) from c1_nom;
```

## 7. Быстрый ответ на типовые вопросы

| Вопрос | Где смотреть |
|---|---|
| Когда объект попал в HiTek | `res.insert_at` в соответствующей коллекции MongoDB |
| Какой ID получил объект в HiTek | `res.ref_id` там же |
| Что именно прислала 1С | `response` в том же документе (сырой ответ) |
| Какому коду 1С отвечает позиция HiTek | `C1_LINKS` по `NOM_ID`, поля `KOD_IZD`/`ART_IZD` |
| Когда импортировался заказ | `C1_ZAKAZ_H.DATE_INPORT` (или `res.insert_at` в `C1_ZC`) |
| Когда сервис вообще работал | `log.connections`, поле `date` |
| Что реально списалось/переместилось | `NOM_TRANS` (не `DOC_ITEMS`) |
