# Как определить, кто куда обращается: 1С, C1CServ, fb-port

Практическая инструкция: где заданы адреса и порты, как выяснить это на живом хосте
и как восстановить картину постфактум, когда сервисы уже не работают.

Проверено по исходникам и на живых хостах 2026-08-13.

---

## 1. Схема обмена (кто кому звонит)

```
1С (веб-сервисы)              C1CServ                fb-port            Firebird
   ◄── GET  /unf/hs/ht/… ──── (клиент)
   ◄── POST /bp_ht/hs/ht_bp/… (клиент)
                               ├── POST /query ────► (клиент) ──► нативный клиент ──► :3050
                               └── mongodb://… ──► MongoDB (журнал соответствий)
```

Важно для поиска: **инициатор всегда C1CServ**. 1С сама никуда не стучится, fb-port
никаких исходящих HTTP не делает (только соединение с Firebird), HiTek не обращается
ни к C1CServ, ни к 1С — он работает с той же базой Firebird напрямую.

## 2. Где что задано: файлы, переменные, хардкод

### 2.1 C1CServ

| Что | Где задано | Значение по умолчанию |
|---|---|---|
| Адрес и порт **прослушивания** | `.env` → `SERVER`, `PORT`; читается в `src/server.ts` | `127.0.0.1:3737` |
| Адрес **1С** | `.env` → `C1_WEBSERVER` | нет, обязателен |
| Адрес **fb-port** | `.env` → `DB_HOST`, `DB_PORT` | нет, обязателен |
| Адрес **MongoDB** | `.env` → `MONGODB_SERVER`, `MONGODB_USER`, `MONGODB_PASSWORD`, `MONGODB_BASE` | порт 27017 зашит в коде |
| Пути HTTP-сервисов 1С | **в коде**: `src/types/ExportSchemes.ts`, поле `servC1Path` каждой схемы | — |

**Файл конфигурации:** `.env` в корне проекта (рядом с `package.json`).
Типовые расположения: `/opt/c1cserv/.env`, `/root/node-app/C1CServ/.env`,
`C:\NodeProjects\C1CServ\.env`. В systemd-развёртывании вместо него может быть
`EnvironmentFile=`, например `/etc/c1-test/c1cserv.env`.

**Перечень всех переменных** — `src/types/environment.d.ts` (это самый быстрый способ
узнать, что вообще ожидает сервис).

**Точки исходящих запросов в коде** (по ним видно, как собирается адрес):

| Куда | Файл:строка | Как формируется URL |
|---|---|---|
| 1С — чтение объектов | `src/modules/1cdata.ts:71` | `http://${C1_WEBSERVER}/${scheme.servC1Path}/${uid}` |
| 1С — создание номенклатуры | `src/modules/fromERP.ts:70` | `http://${C1_WEBSERVER}/bp_ht/hs/ht_bp/nomenclature` ← **путь захардкожен** |
| fb-port | `src/modules/fbquery.ts:13` | `http://${DB_HOST}:${DB_PORT}/query` |
| MongoDB | `src/modules/db.ts:10` | `mongodb://${MONGODB_USER}:${MONGODB_PASSWORD}@${MONGODB_SERVER}:27017/${MONGODB_BASE}` ← **порт 27017 захардкожен** |

**Прочий хардкод, который стоит знать:**
`src/modules/routes.ts` — маршрут `/C1_ZC_FILE` читает список GUID из
`/root/node-app/C1CServ/src/testData/docUID.txt`. Путь Linux-овый и абсолютный: по нему
видно, **где сервис работал в проде**.

### 2.2 fb-port

| Что | Где задано | По умолчанию |
|---|---|---|
| Адрес и порт прослушивания | `.env` → `SERVER`, `PORT`; `src/server.ts` | `127.0.0.1:3333` |
| Адрес **Firebird** | `.env` → `DB_HOST`, `DB_PORT`, `DB_NAME` | нет |
| Учётные данные Firebird | `.env` → `DB_USER`, `DB_PASSWORD` | нет |
| Кэши | `.env` → `CACHE_RES_TTL`, `CACHE_PREPARE_TTL` | 0 |

**Файл:** `.env` в корне проекта. Типовые расположения: `/root/node/fb-port/.env`
(так стоит в проде), `/opt/fb-port/.env`, `/etc/c1-test/fb-port.env` (systemd).

**Строка соединения с Firebird** собирается в `src/modules/db.ts:24`:
`${DB_HOST}/${DB_PORT}:${DB_NAME}` — то есть `DB_NAME` может быть как **алиасом**
(`erp_base_api`), так и **полным путём** (`/var/lib/firebird/erp_base_api_c1.fdb`).
Алиасы описаны на сервере БД в `databases.conf` (см. §4).

Исходящих HTTP-запросов fb-port не делает вовсе.

> ⚠️ **Реальная ловушка из прода:** в `/root/node/fb-port/.env` строка называется
> `RT=3333`, а не `PORT=3333` — опечатка. Переменная `PORT` не задана, и сервис слушает
> порт из умолчания в коде (3333). Совпало случайно; менять порт правкой этой строки
> бесполезно.

## 3. Как определить на живом хосте

Порядок именно такой: сначала что реально работает, потом что написано в конфигах.
Расхождение между ними — самая частая причина «настроили, а не работает».

### Шаг 1. Что слушает и чем запущено

```bash
ss -tlnp | grep -E ':(3737|3738|3333|27017|3050)'
```

Даёт порт и PID. Дальше по PID:

```bash
ls -l /proc/<PID>/cwd          # каталог сервиса
tr '\0' '\n' < /proc/<PID>/environ | grep -E 'PORT|SERVER|DB_|MONGO|C1_'
```

**`/proc/<PID>/environ` — самый достоверный источник:** показывает переменные, с
которыми процесс реально запущен, независимо от того, что лежит в `.env` сейчас.
Нужен root (или тот же пользователь, что владеет процессом).

Причина, по которой это важно: `dotenv` **не перекрывает** уже установленные переменные
окружения. Если сервис запущен через systemd с `EnvironmentFile` или с `Environment=`,
файл `.env` в каталоге проекта может вообще не действовать, хотя и лежит на месте.

### Шаг 2. Как запускается

```bash
systemctl cat c1cserv-test fb-port 2>/dev/null | grep -E 'ExecStart|EnvironmentFile|WorkingDirectory|User'
grep -rl "/opt/c1cserv" /etc/systemd/system/*.service    # найти юнит по каталогу
pm2 list                                                  # в проде fb-port живёт под PM2
ls -la /root/.pm2/logs/                                   # логи PM2, если он есть
```

### Шаг 3. Куда сервис на самом деле обращается

```bash
# что настроено
grep -E 'C1_WEBSERVER|DB_HOST|DB_PORT|MONGODB' /opt/c1cserv/.env /etc/c1-test/c1cserv.env 2>/dev/null

# фактическая база, в которую пишет C1CServ (сквозная проверка до Firebird):
curl -s http://127.0.0.1:3738/test_db | grep -o '"DB_NAME":"[^"]*"'

# живые исходящие соединения процесса
ss -tnp | grep <PID>
lsof -p <PID> -i 2>/dev/null
```

`GET /test_db` особенно полезен: он проходит всю цепочку C1CServ → fb-port → Firebird и
возвращает **имя файла базы, в которую реально идёт запись** — а не то, что написано в
конфиге.

### Шаг 4. Одной командой

Всё перечисленное собирает готовый скрипт:

```bash
ssh <host> 'sudo bash -s' < tools/discover-stack.sh
```

Он находит Firebird (и отличает сервер от клиента), опознаёт базы HiTek по схеме,
находит C1CServ и fb-port **по содержимому каталога**, читает их конфиги, показывает
порты и строит сводку «кто на кого смотрит». Подробности — `tools/README.md`.

## 4. Как определить адрес базы, если в конфиге алиас

Если в `.env` fb-port написано `DB_NAME=erp_base_api` — это алиас, а не путь. Куда он
указывает, написано **на сервере Firebird**:

```bash
grep -vE '^\s*#|^\s*$' /opt/firebird/databases.conf     # tarball-установка
grep -vE '^\s*#|^\s*$' /etc/firebird/*/databases.conf   # установка из пакетов
```

Кто подключён к базе прямо сейчас (видно адрес клиента и путь к его исполняемому файлу):

```sql
select mon$remote_address, mon$remote_process, mon$user
  from mon$attachments where mon$attachment_id <> current_connection;
```

## 5. Как восстановить картину постфактум

Когда сервисы уже не работают, «куда они слали» приходится восстанавливать по следам.
Честно о том, что сохраняется, а что нет:

| Источник | Что даёт | Чего НЕ даёт |
|---|---|---|
| **`.env` установки** | точные адреса 1С, fb-port, Mongo | файл в `.gitignore` — **в git и в бэкапах кода его нет** |
| **MongoDB `c1_data`** | сырые ответы 1С по каждому объекту + `res.insert_at` — доказывает, что обмен шёл, и когда | **адрес 1С не хранится** |
| **Firebird** | записи `C1_NOM`, `C1_LINKS`, `C1_ZAKAZ_H`, `DOC_HEADER` — доказывают факт и время загрузки | адреса нет |
| **Логи сервисов** | C1CServ пишет `axios.get: <путь>` без хоста; fb-port пишет SQL и строку соединения при старте | у C1CServ **хоста 1С в логах нет** |
| **journalctl / PM2** | `journalctl -u <unit> --since …`, `~/.pm2/logs/*.log` | зависит от ротации |
| **Сетевое оборудование** | connection tracking, логи firewall, DNS-кэш роутера | обычно короткая история |

**Ключевой вывод:** единственная надёжная запись адреса 1С — это `.env` рабочей
установки. В бэкапе исходников `.env` отсутствует (он в `.gitignore`), поэтому
исторический адрес восстанавливается только с той машины, где сервис работал, или из
резервной копии этой машины.

Строка соединения с Firebird, наоборот, попадает в лог fb-port **при каждом старте**
(`src/modules/db.ts:25` печатает `connectionString`), так что в журнале systemd/PM2 её
обычно можно найти:

```bash
journalctl -u fb-port | grep -m1 ':' | head -1
grep -m1 'firebird\|:.*fdb' ~/.pm2/logs/fb-port-out.log
```

## 6. Ловушки диагностики

1. **Проверка порта может врать.** В сети, где стоит прозрачный прокси или policy-routing,
   TCP-соединение «устанавливается» с любым адресом и портом. Проверьте контролем:
   ```bash
   for ip in <цель> <заведомо-несуществующий-адрес>; do
     timeout 3 bash -c "</dev/tcp/$ip/80" && echo "$ip открыт" || echo "$ip закрыт"
   done
   ```
   Если «открыт» и заведомо несуществующий — результаты бессмысленны, отвечает посредник.
   То же с `ping`. Достоверна только **прикладная** проверка: осмысленный ответ 1С на
   реальный GUID, ответ fb-port на `/ProcList`, ответ C1CServ на `/test_db`.

2. **`.env` может не действовать.** Если сервис под systemd с `EnvironmentFile`, правка
   `.env` в каталоге проекта ничего не изменит. Смотрите `/proc/<PID>/environ`.

3. **`build/` может быть старше `src/`.** Сервис запускается из `build/server.js`;
   если после правки не выполнен `yarn build`, работает старый код с старым поведением.

4. **Ошибки C1CServ приходят с HTTP 201.** Сбой обмена не виден по коду ответа — он
   лежит в теле, в поле `err.errCode` (10, 20, 30, 40). Смотрите тело, а не статус.

5. **Один и тот же `package.json name`.** У C1CServ и fb-port он одинаковый
   (`typescript_start`) — различать их по имени нельзя. Признаки: fb-port имеет
   зависимость `node-firebird-driver-native`, C1CServ — модуль `src/modules/1cdata.ts`.

## 7. Быстрый чек-лист

```bash
# 1. что работает и на каких портах
ss -tlnp | grep -E ':(3737|3738|3333|27017|3050)'

# 2. с какими переменными реально запущены (root)
for p in $(pgrep -f 'node .*server.js'); do
  echo "== PID $p  $(readlink -f /proc/$p/cwd)"
  tr '\0' '\n' < /proc/$p/environ | grep -E '^(PORT|SERVER|DB_|MONGODB_|C1_)'
done

# 3. сквозная проверка до базы
curl -s http://127.0.0.1:3738/test_db | grep -o '"DB_NAME":"[^"]*"'
curl -s http://127.0.0.1:3333/ProcList | head -c 200

# 4. полное обследование хоста
ssh <host> 'sudo bash -s' < tools/discover-stack.sh
```
