# Этап 2: выгрузка из HiTek по запросу 1С — дизайн

Статус: **проект, реализация не начата**. Подготовлено 2026-08-06 в рамках тестовой платформы.

## 1. Назначение

Обратное направление обмена: 1С периодически запрашивает у HiTek новые документы и движения:

| Сущность | Источник в HiTek | Признак |
|---|---|---|
| Внутреннее перемещение | `DOC_HEADER` + `DOC_ITEMS` | `OPERATION = 2` |
| Отпуск в производство | `DOC_HEADER` + `DOC_ITEMS` (+ связь с заказом через `C1_ZTOD` → `C1_ZAKAZ_H`) | `OPERATION = 3` |
| Выполненные работы | `NOM_PACK_ROUTE` + `RT_ROUTE_ITEMS` + `NOM_PACK` | маршрутные операции партий, «выполнено» = `DATE_E IS NOT NULL` (критерий согласовать) |
| Движение материалов | `NOM_TRANS` (+ операция, партия, склад, документ) | все проведённые движения |

## 2. Размещение

Отдельный сервис **`hitek-export`** в собственном LXC по правилам `/opt/infra-ansible`
(предложение: vmid 144 → 192.168.7.144; роль `roles/hitek-export/`, плейбук
`playbooks/services/hitek-export.yml`, запись в `services.yml`). Node.js + systemd, без docker.

Доступ к данным:
- **Firebird — только через fb-port** (вызовы процедур): прод `firebird5:3333`, тест `c1-test:3333`.
  Прямого SQL у сервиса нет — весь доступ инкапсулируется новыми селект-процедурами `EXP2_*_S`.
- **GUID 1С** для объектов, пришедших из 1С, сервис резолвит из Mongo-журнала
  (`res.ref_id → GUID`, как это уже делает ручка `/C1_GUID` C1CServ); коды 1С — из `C1_LINKS`
  (`KOD_IZD`/`ART_IZD` уже лежат в базе).
- Сетевое условие внедрения: достижимость 1С (192.168.10.58) → LXC сервиса, порт HTTPS/HTTP.

## 3. REST API для 1С

1С удобнее всего: HTTP GET с параметрами, JSON, батчи ограниченного размера, явное
подтверждение получения. Базовый префикс `/exp2/v1`, авторизация — статический
`X-Auth-Token` + IP-allowlist (публикации наружу нет).

| Метод | Назначение |
|---|---|
| `GET /exp2/v1/transfers?limit=100` | пакет внутренних перемещений |
| `GET /exp2/v1/production_issues?limit=100` | пакет отпусков в производство |
| `GET /exp2/v1/works?limit=500` | пакет выполненных маршрутных операций |
| `GET /exp2/v1/material_moves?limit=1000` | пакет движений материалов |
| `POST /exp2/v1/ack` `{"ИдПакета":"<uuid>"}` | квитирование пакета (идемпотентно) |
| `GET /exp2/v1/state` | диагностика: курсоры, открытые пакеты |

## 4. Инкрементальность и гарантии доставки

Канонический курсор — **монотонный ID** (`DOC_ID`, `TRANS_ID`, `PACK_ROUTE_ID`), не даты
(даты не монотонны и правятся задним числом).

Выбранная схема — **серверное квитирование** (рекомендована; альтернатива «курсор хранит 1С»
отвергнута: потеря курсора в 1С = массовая повторная выгрузка):

1. Состояние в таблице `EXP2_BATCH (BATCH_ID char(36), ENTITY varchar(31), FROM_ID, TO_ID,
   STATE smallint /*0=open,1=acked*/, DATE_OPEN, DATE_ACK)`.
2. `GET` без параметров: если по сущности есть **открытый** пакет — сервис повторно отдаёт
   **его же** (redelivery: сбой 1С ничего не теряет); иначе открывает новый от последнего
   acked `TO_ID`.
3. `POST /ack {ИдПакета}` закрывает пакет и двигает курсор. Повторный ack того же пакета — no-op.
4. Семантика **at-least-once**; дедупликация на стороне 1С по `ИдHiTek`
   (идемпотентная загрузка: «документ с таким ИдHiTek уже есть — пропустить»).

## 5. Новые процедуры Firebird (только SELECT — совместимы с fb-port)

| Процедура | Возврат (эскиз) |
|---|---|
| `EXP2_DOC_TRANSFER_S(FROM_ID, MAX_ROWS)` | шапки OPERATION=2: `DOC_ID, NUMBER, DATE_DOC, STORAGE_OUT(+NAME), STORAGE_IN(+NAME), REGISTED, DESCRIPT`; `DELETED=0 and DOC_ID > :FROM_ID order by DOC_ID rows :MAX_ROWS` |
| `EXP2_DOC_ISSUE_S(FROM_ID, MAX_ROWS)` | то же для OPERATION=3 + `ZAKAZ_NUM` (join `C1_ZTOD` → `C1_ZAKAZ_H`) |
| `EXP2_DOC_ITEMS_S(DOC_ID)` | `ITEM_ID, NOM_ID, KOD_IZD (join C1_LINKS), NOM_NAME, CNT, MEASURE, PACK_ID, STORAGE_ID` |
| `EXP2_WORKS_S(FROM_ID, MAX_ROWS)` | из `NOM_PACK_ROUTE`(+`RT_ROUTE_ITEMS`,`NOM_PACK`): `PACK_ROUTE_ID, PACK_ID, NOM_ID, OPER_NUM, DESCRIPT, CNT_IN, CNT_OUT, CNT_DEFECT, DATE_B, DATE_E, EMPLOYEE_ID, STR_ID, TIME_SEC` |
| `EXP2_NOM_TRANS_S(FROM_ID, MAX_ROWS)` | `TRANS_ID, OPER_ID(+имя), PACK_ID, NOM_ID, KOD_IZD, CNT, STORAGE_ID(+NAME), DATE_TRANS, ITEM_ID, DOC_ID(+NUMBER), STATUS` |
| `EXP2_BATCH_OPEN_IU(ENTITY, BATCH_UUID, MAX_ROWS)` / `EXP2_BATCH_ACK_U(BATCH_UUID)` / `EXP2_STATE_S(ENTITY)` | управление квитированием + DDL `EXP2_BATCH` |

Обкатка процедур — на тестовом клоне `erp_base_api_c1` (алиас `db_hitek_api_c1`) через
платформу этого репозитория; 1С на этапе тестов эмулируется теми же средствами
(curl/скрипт вместо реального 1С-клиента).

## 6. Открытые вопросы (согласовать до реализации)

1. **Критерий выгрузки**: «только проведённые» (`REGISTED=1`)? На момент аудита в базе нет
   ни одного документа с `REGISTED=1` — фильтр должен быть конфигурируемым.
2. Критерий «выполненности» работ (`DATE_E IS NOT NULL`? отметки оператора?).
3. Нужна ли 1С отмена/сторно (документ удалён/распроведён в HiTek после выгрузки) —
   отдельная сущность «ОтменённыеДокументы» или флаг в повторной выдаче.
4. Формат номенклатуры без связи с 1С: создавать автоматически через `/ERP_NEW_NOM` или
   отклонять строку.
5. Частота опроса 1С и размер батчей по каждой сущности.
